# DECISIONS.md — журнал архитектурных решений

Формат записи: Дата | Контекст | Решение | Последствия

---

## D-001 | 2026-10-19 | Целевая платформа
Контекст: нужна ОС для личного ПК, отладка через VM.
Решение: x86-64, тесты в QEMU/KVM, реальное железо с этапа M4+.
Последствия: UEFI+BIOS загрузка, драйверы для типичного consumer-железа (AHCI, e1000/RTL, HDA).

## D-002 | 2026-10-19 | Язык ядра
Контекст: заказчик знает Python (курс), немного C++; важны безопасность и обучение.
Решение: Rust (no_std) для ядра и системных сервисов.
Последствия: нужно изучить Rust (2–4 недели до продуктивного кода); минимум UB; экосистема no_std-крейтов.

## D-003 | 2026-10-19 | GUI-стек
Контекст: нужен интерфейс «как Windows 10», без нарушений АП Microsoft.
Решение: Qt 6 / C++ для shell и приложений; визуальные паттерны воспроизводятся своей отрисовкой; ассеты (шрифты/иконки/звуки) — только свободные (PT Sans OFL, свои иконки).
Последствия: LGPL при динамической линковке совместима с закрытым/свободным кодом приложения; нужен свой QPA-плагин для window server (этап M4).

## D-004 | 2026-10-19 | Python вне системы
Контекст: обсуждали Python для сервисов/GUI.
Решение: Python не используется в ядре, сервисах и winserv. Только как язык будущих пользовательских скриптов (опционально, Phase 2).
Последствия: нет GIL/интерпретатора в критическом пути; разработка приложений на C++.

## D-005 | 2026-10-19 | EXE-совместимость
Контекст: хочется запускать .exe, но это огромная работа (Win32 API эмуляция уровня Wine).
Решение: исключено из MVP; пересмотр после M5.
Последствия: нативные приложения — свои ELF; формат PE-загрузчик — отдельный проект в будущем.

## D-006 | 2026-10-19 | Минимум чужого кода («чистая комната»)
Контекст: требование заказчика — меньше стороннего кода, никаких претензий по АП.
Решение: код пишется с нуля; допускается только open-source с лицензиями MIT/Apache/BSD/LGPL (динамически); запрещено чтение исходников Windows/реверс его бинарей; спецификации форматов (ELF, ext2, FAT, AHCI) — публичные стандарты, использовать можно.
Последствия: медленнее, чем брать готовое; ниже юридические риски.

## D-007 | 2026-10-19 | Локализация
Контекст: желание полностью русскоязычной системы.
Решение: UI и данные — русский (UTF-8); технический слой (ABI, пути, протоколы) — ASCII.
Последствия: нет проблем с сетью/форматами; полная кириллизация путей — отложена как эксперимент Phase 2.

## D-008 | 2026-10-19 | Название ОС
Контекст: нужно имя, которое можно сменить перед релизом без правок по всему коду.
Решение: «ИрНа». Имя вынесено в единый реестр `branding.md` + константы
(`branding/name.h`, `kernel/src/brand.rs`, `bootloader/config.toml`). Хардкод имени в коде запрещён.
Последствия: переименование = правка 1–2 файлов + пересборка; идентификатор `irna` (ASCII), отображение `ИрНа` (UTF-8).

## D-009 | 2026-10-19 | Лицензия проекта
Контекст: выбор MIT vs GPL v3.
Решение: **MIT**.
Последствия: максимальная свобода повторного использования; совместима с Qt (LGPL, динамическая линковка) и всеми planned-зависимостями; сторонние форки не обязаны раскрывать код.

## D-010 | 2026-10-19 | Оконный сервер
Контекст: свой winserv vs wlroots (быстрее).
Решение: **собственный window server** (C++), без X11/Wayland.
Последствия: +1–2 месяца к M3, но минимум чужого кода (D-006) и полный контроль; в M4 потребуется свой QPA-плагин Qt.

## D-011 | 2026-10-19 | Обоснование шрифта PT Sans
Контекст: заказчик спросил, что особенного в PT Sans.
Решение: кандидат №1; альтернативы — DejaVu Sans, Noto Sans.
**Подтверждено заказчиком 2026-10-24:** PT Sans — интерфейс, PT Mono — терминал/консоль.
Аргументы за PT Sans:
- Создан по госзаказу РФ («Программы "Русский язык"»), распространяется по свободной лицензии **SIL Open Font License** — использование и встраивание в ОС легально и бесплатно.
- Разработан специально для кириллицы: полный охват символов, корректные формы букв (в отличие от западных шрифтов, где кириллица часто «доделана»).
- Визуально нейтральный гротеск, близок по духу к Segoe UI — подходит под стиль интерфейса «как Windows 10» (сам Segoe UI брать нельзя — проприетарен).
- Есть фиксированная версия PT Mono для терминала/кода.

## D-012 | 2026-10-19 | Рабочая среда разработки
Контекст: основной ПК — Lenovo (AMD A10-7800B, 8 ГБ RAM, Windows 10); ноутбук IdeaPad 10 (4 ГБ) — только потребление медиа.
Решение: разработка на основном ПК, WSL2 Ubuntu как тулчейн; QEMU/KVM внутри WSL2.
Последствия: 8 ГБ хватит (Windows ~3–4 + WSL2 ~2–4); при нехватке — лимит `.wslconfig`. Ноутбук в проекте не участвует.

## D-013 | 2026-10-24 | Копия Multiboot2 MBI до включения paging
Контекст: GRUB может разместить MBI в области, пересекающейся с `.bss` ядра
(в наблюдаемой раскладке — внутри стека). Парсер MBI читал адрес переменной
вместо её значения, а magic искал в самой структуре, где его нет (magic
приходит в EAX, по смещению 0 лежит `total_size`).
Решение: в 32-битном trampoline (`arch.asm`), до настройки page tables и до
использования стека, MBI копируется в статический буфер `.mbi_copy` (8 КиБ),
размещённый в начале образа. Rust-код работает только с копией; magic
проверяется по сохранённому EAX, `total_size` читается из offset 0.
Последствия: MBI не зависит от раскладки `.bss`/стека; буфер занимает 8 КиБ
в первом PT_LOAD; MBI больше 8 КиБ усекается (для M1 достаточно).

## D-014 | 2026-10-24 | PS/2: scancode set 1 через трансляцию 8042, явный `0xF4`
Контекст: после POST клавиатура может остаться в состоянии «scan disabled»
(`0xF5`); настройка конфигурационного байта 8042 сама по себе сканирование не
включает. Контроллер умеет транслировать set 2 → set 1 (bit6 конфиг-байта),
что позволяет держать в ядре один простой декодер.
Решение: включаем трансляцию (bit0 IRQ1, bit6 translation, bit4 снят), затем
`0xAE` и явную команду `0xF4` (enable scanning). IRQ1 только складывает байты в
SPSC-кольцо; разбор (make/break, `0xE0`, Shift, ASCII) — в `poll()` главного
потока. Раскладка — US ASCII; EN/RU и кириллица откладываются до framebuffer.
Последствия: драйвер не блокируется в прерывании, не требует мьютексов; ответ
`0xFA` на `0xF4` проходит через IRQ1 и подтверждает живой канал. Для headless-
тестов клавиша вводится через QMP `input-send-event` (HMP `sendkey` не работает
при `-display none`).

## D-015 | 2026-10-24 | Framebuffer: request-тег MB2 type=5 + 2-МиБ identity-map
Контекст: для консоли с кириллицей нужен линейный framebuffer. Раньше считалось,
что GRUB 2.06 не поддерживает request-теги framebuffer («unsupported tag 0x14»),
но корень был в битом заголовке M0: теги собирались в смешанном формате
`dw`/`dd`, и GRUB читал мусорные типы.
Решение: заголовок MB2 приведён к каноническому виду (`dd type`/`dd size`,
выравнивание по 8 байт), добавлен тег type=5 с `1024×768×32`;
`header_length=64`. GRUB сам формирует `gfxpayload` из полей тега и
переключает режим — `set gfxpayload` в `grub.cfg` не нужен. LFB у QEMU лежит
выше 1 ГиБ (`0xFD000000`), поэтому `paging.rs` достраивает identity-map
страницами по 2 МиБ RW из статического пула (8 page tables, 32 КиБ).
Ядро не предполагает bpp и порядок каналов: всё берётся из тега 8, поддержаны
24 и 32 bpp.
Последствия: режим на разных машинах разный (в тестовом окружении GRUB отдаёт
800×600×24); пул page tables не освобождается — полноценный VM-менеджер в M2.

## D-016 | 2026-10-24 | Консольный шрифт: PT Mono 10×16, растр из TTF (OFL)
Контекст: D-011 фиксирует PT Sans для интерфейса и PT Mono для терминала.
VGA-ROM (CP437) кириллицу не содержит, Unifont — временное решение с чужим
дизайном.
Решение: консоль ядра использует PT Mono Regular (PTM55FT.ttf, ParaType,
SIL OFL 1.1). Глифы растрируются `tools/gen-font8x16.ps1` в сетку 10×16
(`SingleBitPerPixelGridFit`, без сглаживания), упаковка — `[[u16; 16]; 165]`
(ASCII, кириллица А-я, Ё/ё, `– — « »`), старший бит — левый пиксель.
Ячейка 10 px, а не 8: при кегле 12 PT Mono шире 8 px и обрезался справа.
Последствия: шрифт — сгенерированный файл `kernel/src/font.rs` (в git, без
зависимости от TTF при сборке); превью — `tools/preview-font8x16.ps1`;
лицензия — `assets/fonts/OFL-PT-Mono.txt`. Для UI в M3/M4 по-прежнему
планируется полноценный рендер TTF (PT Sans/PT Mono), bitmap — только консоль.

## D-017 | 2026-10-24 | SYSCALL/SYSRET: Linux-подобный ABI, статический стек входа
Контекст: M1 нужен минимальный системный вызов, чтобы проверить переход
ring 3 → ring 0 → ring 3 и подготовить M2 (процессы, libc).
Решение: `EFER.SCE=1`; `STAR[47:32]=0x08` (вход: CS=0x08, SS=0x10),
`STAR[63:48]=0x13` (выход: CS=0x23, SS=0x1B — поэтому в GDT user-data идёт
перед user-code); `LSTAR=syscall_entry`; `FMASK=0x47700` (TF|IF|DF|NT|AC).
ABI — Linux-подобный: номер в RAX, аргументы RDI/RSI/RDX/R10/R8/R9, результат
в RAX, ошибка — отрицательный errno. Реализованы `write` (fd 1/2 → serial +
консоль) и `exit`; `read` возвращает `-ENOSYS` до появления планировщика.
Вход сохраняет user RSP в статическую переменную и переключается на отдельный
стек 16 КиБ; выход из `exit` — на основной стек ядра + `sti`.
Последствия: вложенные syscall из ring 0 не поддерживаются (одно ядро, один
поток). В M2 заменим на per-CPU GS-базу + `swapgs`. Буфер `write` читается
напрямую (SMAP выключен) — `copy_from_user` появится вместе с процессами.
Smoke-тест ring 3 — машинный код в `kernel/src/user.rs`, не ELF.
