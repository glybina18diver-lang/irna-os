# TECH-DEBT — реестр технического долга «ИрНа»

> Здесь собраны **сознательные упрощения M1**, которые уже работают, но не
> годятся для следующих этапов. Это не список багов: каждый пункт — известное
> ограничение с планом закрытия.
>
> Актуально на **2026-10-24**, этап **M1**. Связанные документы:
> `docs/STATE.md`, `ROADMAP.md`, `DECISIONS.md`, `docs/BUILD.md`.

## Как вести реестр

- ID `TD-NNN` не переиспользуются и не удаляются. Закрытая запись остаётся
  в файле со статусом `closed` и ссылкой на коммит/решение.
- Приоритет:
  - **P0** — блокирует корректность или безопасность; чинить до расширения
    функциональности;
  - **P1** — закрыть до конца текущего этапа или в начале следующего;
  - **P2** — можно отложить, есть рабочий обход.
- Если закрытие требует архитектурного выбора — сначала запись `D-NNN`
  в `DECISIONS.md`, затем ссылка на неё из записи долга.
- Закрывая долг, обновляйте `HISTORY.md` и `docs/STATE.md`.

## Память

### TD-001 — PMM ограничен 128 МиБ

**Где:** `kernel/src/pmm.rs` (`MAX_FRAMES = 128 * 1024`, `top` обрезается до
`0x0800_0000`).

**Почему так:** bitmap лежит в `.bss` и должен быть доступен до появления
полноценной карты памяти; массив рассчитан на 512 МиБ
(`[u64; MAX_FRAMES / 64]` = 16 КиБ), но рабочий предел обрезан до 128 МиБ.

**Последствия:** в QEMU с `-m 512` загрузчик сообщает `free_mem_top =
0x1FFE0000`, но ядро видит только `PMM frames total = 32768` (128 МиБ).
Остальная память не используется; `alloc_frame()` вернёт `None` при
исчерпании пула.

**План:** в M2 перейти на bitmap по фактическому размеру памяти (или
несколько уровней), размещать его через PMM, а не в `.bss`; снять зависимость
от identity-map trampoline.

**Критерий закрытия:** `PMM frames total` соответствует карте загрузчика
(для `-m 512` — около 131 000 кадров), аллокация работает выше 128 МиБ.

---

### TD-002 — Статический пул page tables, нет освобождения

**Где:** `kernel/src/paging.rs` (`PT_POOL_COUNT = 8`, `PT_USED`), `map_identity_2m`,
`map_user_4k`.

**Почему так:** для M1 нужно было отобразить LFB выше 1 ГиБ и две
пользовательские страницы; пул из 8 таблиц (32 КиБ) покрывает это с запасом.

**Последствия:**
- после исчерпания пула `map_*` возвращает `false` — без диагностики причины;
- нет `unmap`, нет возврата таблиц, нет учёта владельца;
- поддерживается только `pml4[0]` (0…512 ГиБ), адреса вне диапазона
  отклоняются;
- сброс TLB — перезагрузкой CR3 (глобальный, а не по странице).

**План:** M2 — VM-менеджер: дерево таблиц на адресное пространство, `map/unmap`,
учёт ссылок, `invlpg`, физические страницы под таблицы из PMM.

**Критерий закрытия:** таблицы выделяются и освобождаются динамически;
есть тест на `map → unmap → map` без утечки.

---

### TD-003 — Bump-heap на 1 МиБ без освобождения

**Где:** `kernel/src/heap.rs` (`POOL_SIZE = 1 MiB`, `NEXT: AtomicUsize`).

**Почему так:** нужен `#[global_allocator]` для `alloc::format!` и
`String`; bump-аллокатор — минимальный рабочий вариант.

**Последствия:**
- размер выделения округляется вверх до степени двойки (минимум 32 байта),
  выравнивание — до 64;
- `dealloc` ничего не делает, память не возвращается;
- при исчерпании пула `alloc` возвращает null (без паники);
- пул статический: +1 МиБ к образу ядра в `.bss`.

**План:** M2 — slab для мелких объектов + buddy/списки свободных блоков для
крупных; `dealloc`/`realloc`; статистика занятости.

**Критерий закрытия:** цикл `alloc/free` 100 000 раз не увеличивает
потребление; есть счётчик свободной памяти.

---

### TD-004 — Нет NX, SMAP/SMEP и `copy_from_user` (**P0**)

**Где:** `kernel/src/syscall.rs` (`sys_write` читает буфер напрямую),
`kernel/src/paging.rs` (флаги `P|RW|US`, без `NX`), `kernel/src/user.rs`.

**Почему так:** в M1 пользовательские страницы видны ядру в том же адресном
пространстве; SMAP/SMEP требуют настройки CR4 и аккуратной работы с `stac/clac`.

**Последствия:**
- любая страница исполняема: NXE (EFER.NXE) не включён;
- ядро доверяет указателю из ring 3: проверяются только `buf != 0` и
  `len <= 4096`, диапазон/права страницы — нет;
- включение SMAP «как есть» сломает `sys_write`, пока нет `copy_from_user`.

**План:** M2 — `copy_from_user`/`copy_to_user` с проверкой диапазона и
`stac/clac`, включить EFER.NXE и помечать данные NX, затем SMEP/SMAP.

**Критерий закрытия:** передача ядру указателя на неотображённую/чужую
страницу возвращает `-EFAULT`, а не роняет ядро; код user-страниц NX-совместим.

## Планировщик и задачи

### TD-005 — Только кооперативный планировщик

**Где:** `kernel/src/sched.rs` (`yield_now`, `run`), `kernel/src/main.rs`
(3 демо-задачи).

**Почему так:** сначала нужно было проверить `switch_context` и стек на задачу
без риска гонок с IRQ0.

**Последствия:** задача, не вызвавшая `yield_now`, занимает CPU навсегда;
нет приоритетов, квантов, `sleep`, блокировок и ожидания событий; `run()`
возвращает управление, когда готовых задач не осталось.

**План:** M1 — переключение из IRQ0 по PIT (вытеснение), состояние `Running`,
квант; M2 — приоритеты и блокирующие примитивы.

**Критерий закрытия:** задача с бесконечным циклом не мешает остальным;
переключение происходит по тику таймера.

---

### TD-006 — Статические стеки задач без guard pages

**Где:** `kernel/src/sched.rs` (`MAX_TASKS = 8`, `STACK_SIZE = 16 KiB`,
`static mut STACKS`).

**Почему так:** просто и предсказуемо для smoke-теста; не нужен PMM.

**Последствия:** 8 × 16 КиБ = 128 КиБ в `.bss`; переполнение стека молча
затирает соседнюю задачу или данные ядра; нет защиты и диагностики.

**План:** M2 — стек из PMM, guard page (неотображённая страница) снизу,
проверка `RSP` при переключении, освобождение при завершении задачи.

**Критерий закрытия:** переполнение стека даёт контролируемый `#PF`, а не
порчу памяти.

---

### TD-007 — Нет смены CR3 и адресных пространств

**Где:** `kernel/src/sched.rs`, `kernel/src/paging.rs`.

**Почему так:** все задачи — функции ядра в общем адресном пространстве;
процессов в M1 нет.

**Последствия:** задачи не изолированы; нельзя запустить два разных
пользовательских образа; `CURRENT`/`MAIN_RSP` — глобальные `static mut`.

**План:** M2 — `AddressSpace` на процесс, `switch_context` дополнительно
меняет CR3 (или отложенно, по флагу), отдельные kernel-стеки.

**Критерий закрытия:** две user-программы работают одновременно и не видят
память друг друга.

---

### TD-008 — `spawn` не сигнализирует переполнение

**Где:** `kernel/src/sched.rs` (`spawn -> bool`), `kernel/src/main.rs`
(результат игнорируется).

**Почему так:** в демо ровно 3 задачи при лимите 8.

**Последствия:** при 9-й задаче она не запускается, ядро продолжает работу
без сообщения; отладка усложняется.

**План:** логировать отказ, вернуть `Result`/код ошибки, добавить счётчик
отказов в диагностику.

**Критерий закрытия:** попытка создать 9-ю задачу видна в serial-логе.

---

## Syscall и user space

### TD-009 — Статический стек входа, нет вложенности

**Где:** `kernel/src/arch.asm` (`syscall_entry`, статический стек и переменная
сохранённого user RSP), `kernel/src/syscall.rs`.

**Почему так:** один поток, один пользовательский контекст; экономит память и
упрощает отладку.

**Последствия:** повторный `syscall` из обработчика затрёт сохранённый RSP;
прерывания на время обработчика запрещены (`FMASK`); нет per-CPU структур.

**План:** M2 — стек syscall на задачу/CPU, вложенность, аккуратная работа с
`IF`, сохранение контекста в `Task`.

**Критерий закрытия:** syscall из обработчика (или после вытеснения) не
повреждает возврат в user mode.

---

### TD-010 — Минимальный syscall ABI

**Где:** `kernel/src/syscall.rs` (`SYS_READ = 0`, `SYS_WRITE = 1`,
`SYS_EXIT = 60`).

**Почему так:** M1 проверяет саму цепочку SYSCALL/SYSRET, а не POSIX.

**Последствия:**
- `read` всегда `-ENOSYS`; нет `open/close/brk/mmap/fork/execve`;
- нет таблицы файловых дескрипторов: `write` принимает только fd 1 и 2;
- нет `errno`-структуры, только отрицательный код;
- буфер ограничен 4096 байтами;
- неизвестный номер печатается в serial и возвращает `-ENOSYS`.

**План:** M2 — таблица fd, `read` с блокировкой, базовый набор POSIX,
отдельный `errno`.

**Критерий закрытия:** user-программа читает ввод через `read(0, ...)`, а не
через прямой доступ к буферу клавиатуры.

---

### TD-011 — Нет ELF-загрузчика, user-программа зашита в ядро

**Где:** `kernel/src/user.rs` (адреса `0x40_0000`/`0x40_2000`, массив из 33
байт машинного кода, сообщение по смещению `0x40`).

**Почему так:** для smoke-теста ring 3 достаточно одной страницы кода и одной
страницы стека.

**Последствия:** нельзя загрузить внешний бинарник; адреса фиксированы; после
записи кода страница переводится в RO, но полноценной защиты нет (см. TD-004);
нет `argv/envp`, нет точки входа ELF.

**План:** M2 — парсер ELF64, раскладка сегментов по адресному пространству,
стек с аргументами, запуск из VFS.

**Критерий закрытия:** `init` собирается отдельно и загружается ядром как ELF.

---

### TD-012 — `exit` всегда возвращает в echo-loop

**Где:** `kernel/src/arch.asm` (`syscall_exit_to_kernel`),
`kernel/src/user.rs` (`kernel_after_user`).

**Почему так:** в M1 ровно один тестовый процесс; после него ядро должно
продолжить работу и проверить IRQ1.

**Последствия:** нет завершения процесса, освобождения страниц и возврата в
планировщик; повторный запуск user-теста невозможен без перезагрузки.

**План:** M2 — `exit` помечает процесс завершённым, освобождает адресное
пространство и переключает на следующую задачу.

**Критерий закрытия:** после `exit` планировщик продолжает работу, ресурсы
процесса освобождены.

## Загрузка, видео, ввод

### TD-013 — GRUB отдаёт 800×600×24 вместо запрошенных 1024×768×32

**Где:** `kernel/src/arch.asm` (request-тег type=5), `kernel/src/bootinfo.rs`
(разбор тега 8), `kernel/src/fb.rs`.

**Почему так:** в текущем окружении QEMU/GRUB VBE-режим 1024×768 недоступен;
ядро сознательно читает `bpp/pitch/каналы` из тега и не привязано к режиму.

**Последствия:** фактическая консоль — 800×600, 80×37 символов; масштаб 2×
включается только при высоте ≥ 700 px, поэтому здесь глифы 10×16 без
увеличения. На реальном железе режим может отличаться.

**План:** M2/M3 — собственный выбор режима (VBE/EFI GOP) или фиксированный
режим через загрузчик; тест на нескольких разрешениях.

**Критерий закрытия:** ядро само устанавливает запрошенный режим или явно
сообщает фактический и работает на нём без эвристик.

---

### TD-014 — VGA text fallback без кириллицы

**Где:** `kernel/src/vga.rs` (UTF-8 → CP437), `kernel/src/console.rs`.

**Почему так:** ROM-шрифт VGA содержит CP437, где нет кириллицы; LFB —
основной путь.

**Последствия:** при отсутствии тега framebuffer русский текст превращается в
`?`; сообщения ядра частично теряют смысл.

**План:** M3 — либо полностью отказаться от VGA text, либо загрузить свой
шрифт в VGA (перерисовка знакогенератора).

**Критерий закрытия:** fallback-режим отображает тот же набор глифов, что LFB.

---

### TD-015 — Шрифт нельзя перегенерировать в CI

**Где:** `kernel/src/font.rs` (165 глифов 10×16), `tools/gen-font8x16.ps1`,
`assets/fonts/OFL-PT-Mono.txt`.

**Почему так:** глифы сгенерированы из `PTM55FT.ttf` через Windows
PowerShell + `System.Drawing`; TTF в репозиторий не добавлен (только текст
лицензии OFL), чтобы не тащить бинарный ассет.

**Последствия:** `font.rs` — сгенерированный и закоммиченный файл; изменить
набор символов можно только на Windows с установленным PT Mono. Linux/CI
перегенерировать шрифт не могут.

**План:** M2 — либо положить TTF в `assets/fonts` с фиксацией лицензии, либо
переписать генератор на кроссплатформенный (Python + fonttools) и добавить
шаг проверки в CI.

**Критерий закрытия:** `font.rs` воспроизводится одной командой на Linux.

---

### TD-016 — Раскладка только US, нет RU/AltGr/мыши

**Где:** `kernel/src/keyboard.rs` (scancode set 1, таблица ASCII, Shift).

**Почему так:** M1 проверяет IRQ1 и базовый ввод; кириллица уже есть в шрифте,
но не в раскладке.

**Последствия:** русские буквы с клавиатуры не вводятся; нет `AltGr`,
`Caps Lock` (в текущем декодере), мёртвых клавиш; байты мыши отбрасываются.

**План:** M1 — раскладка EN/RU с переключением (например, `Alt+Shift` или
`Ctrl+Shift`), состояние модификаторов; M2 — мышь PS/2 и события ввода.

**Критерий закрытия:** в echo-loop можно набрать «Привет» и переключить
раскладку без перезагрузки.

## Сборка, CI и документация

### TD-017 — CI не загружает ISO в QEMU

**Где:** `.github/workflows/build.yml`.

**Почему так:** workflow ставит только сборочные зависимости; QEMU-прогон
делается вручную на ноутбуке.

**Последствия:** регрессия, которая ломает загрузку, но не компиляцию,
обнаруживается только после скачивания артефакта. «Зелёный CI» ≠ «ISO
загружается».

**План:** добавить job с `qemu-system-x86` и `ci/run-qemu.sh check` (или
`-display none` + serial-лог) на Ubuntu; публиковать лог как артефакт.

**Критерий закрытия:** CI падает, если пропал любой из маркеров
`M1 subsystems OK`, `sched: tasks done = 3`, `syscall/sysret round-trip OK`.

---

### TD-018 — Артефакты вручную, без релизов и контрольных сумм

**Где:** `.github/workflows/build.yml` (artifact `irna-iso`),
`docs/BUILD.md`.

**Почему так:** этап M1, версий и установщика ещё нет.

**Последствия:** ISO скачивается по номеру run вручную; нет тега версии,
SHA-256 и истории сборок; старый артефакт можно спутать с новым.

**План:** M2 — GitHub Release по тегу, `sha256sum` в артефактах, короткая
запись «что внутри» в описании релиза.

**Критерий закрытия:** есть релиз с ISO, ELF и контрольной суммой.

---

### TD-019 — ISO собирается только на Linux

**Где:** `ci/build.sh`, `docs/BUILD.md`.

**Почему так:** `grub-mkrescue`, `xorriso`, `mtools` и `grub-pc-bin` —
Linux-инструменты; на ноутбуке (Windows, 4 ГБ RAM) нет Rust/NASM.

**Последствия:** локально нельзя собрать ISO; цикл «правка → push → CI →
скачать → QEMU» занимает минуты. Это принятое ограничение окружения, а не
временный дефект.

**План:** не закрывать; при необходимости — контейнер/CI как единственный
сборочный путь. Следить, чтобы `ci/build.sh` оставался единственным источником
правды о сборке.

**Критерий:** документировано и не пытаемся собирать ISO на Windows.

---

### TD-020 — Расхождения в документации

**Где:** `docs/BUILD.md`, `ci/run-qemu.ps1`, `docs/STATE.md`.

**Что было:** `BUILD.md` указывал только
`C:\Projects\OS\tools\qemu\...`, а `run-qemu.ps1` сначала ищет
`C:\Program Files\qemu\...`; `-m 256M` в примерах против `-m 512` в скрипте;
`STATE.md` содержал устаревший хеш коммита.

**Последствия:** новый разработчик запускает не тот путь/режим и получает
«QEMU не найден» или другую карту памяти.

**План:** постоянно — при изменении скрипта обновлять `BUILD.md` и
`QUICKSTART.md`; сверять `STATE.md` с `git log` в конце сессии.

**Критерий закрытия:** `QUICKSTART.md` и `BUILD.md` воспроизводят один и тот
же цикл без правок.

## Ядро, прерывания, диагностика

### TD-021 — `static mut` и общее состояние без блокировок

**Где:** `kernel/src/sched.rs`, `kernel/src/heap.rs`, `kernel/src/pmm.rs`,
`kernel/src/paging.rs`, `kernel/src/main.rs`.

**Почему так:** однопроцессорная машина, прерывания короткие, часть счётчиков
атомарная.

**Последствия:** нет мьютексов/спинлоков; при вытеснении из IRQ0 (TD-005)
гонки станут реальными; `static mut` требует `unsafe` и легко приводит к
алиасингу.

**План:** M2 — спинлоки с запретом прерываний, инкапсуляция состояния в
`struct` с `UnsafeCell`/атомиками, аудит всех `static mut`.

**Критерий закрытия:** вытесняющий планировщик работает без гонок; нет
необоснованных `static mut` в горячем пути.

---

### TD-022 — Нет автотестов, только serial-маркеры

**Где:** `ci/run-qemu.ps1`, `ci/run-qemu.sh`, `kernel/src/main.rs`.

**Почему так:** ядро `no_std`, тестовая инфраструктура не заведена; проверка
идёт по строкам в serial.

**Последствия:** нельзя точечно проверить функцию; ошибка в форматировании
строки ломает «тест»; нет регрессионного набора для PMM/heap/планировщика.

**План:** M2 — unit-тесты для чистых модулей (bitmap, декодер scancode,
парсер MBI) через `#[cfg(test)]` + хост-раннер; для ядра — набор маркеров и
QEMU-job в CI.

**Критерий закрытия:** `cargo test` на хосте покрывает аллокаторы и парсеры;
CI проверяет загрузку ISO.

---

### TD-023 — Только PIC 8259A и PIT

**Где:** `kernel/src/pic.rs`, `kernel/src/pit.rs`, `kernel/src/irq.rs`.

**Почему так:** legacy-путь проще и работает в QEMU/BIOS.

**Последствия:** 16 линий IRQ, нет MSI, нет APIC/IOAPIC, нет HPET/TSC-deadline;
на реальном железе возможны конфликты и низкое разрешение таймера (10 мс).

**План:** M3/M4 — определить ACPI-таблицы (MADT/HPET), перейти на Local APIC
и IOAPIC, таймер — HPET или TSC-deadline.

**Критерий закрытия:** прерывания работают через APIC, PIT остаётся fallback.

---

### TD-024 — Только BIOS + Multiboot2/GRUB

**Где:** `kernel/src/arch.asm` (Multiboot2-заголовок), `ci/build.sh`
(`grub-mkrescue`, BIOS-only, `GRUB_EFI_IMAGES=""`).

**Почему так:** QEMU i440fx/SeaBIOS — самый короткий путь до загрузки ядра.

**Последствия:** нет EFI-загрузки, нет своего загрузчика, ISO не грузится на
UEFI-only машинах; `ci/run-qemu.sh efi` существует, но ISO для EFI не
собирается.

**План:** M6 — EFI-образ (OVMF) и/или собственный загрузчик; отдельный
артефакт `irna-iso-efi`.

**Критерий закрытия:** ISO загружается и в BIOS, и в UEFI.

---

### TD-025 — IDT: 48 гейтов, только `#DF` на IST

**Где:** `kernel/src/idt.rs`.

**Почему так:** M1 закрывает 32 исключения и 16 IRQ; остальные векторы не
используются.

**Последствия:** нет `int 0x80` (syscall только через `syscall`), нет
отдельных IST для `#NMI`/`#MC`/`#DB`; ошибка в обработчике может привести к
triple fault.

**План:** M2 — IST для NMI/MCE/DB, вектор `int 0x80` как legacy-путь при
необходимости, проверка стека исключений.

**Критерий закрытия:** `#NMI` и `#MC` обрабатываются на своих стеках.

---

### TD-026 — Panic и исключения без трассировки

**Где:** `kernel/src/main.rs` (`panic_handler`), `kernel/src/idt.rs`.

**Почему так:** на M1 достаточно факта останова и сообщения в serial.

**Последствия:** нет backtrace, дампа регистров (кроме кадра исключения) и
символов; причина паники восстанавливается вручную.

**План:** M2 — вывод регистров, разбор стека по `RBP`/unwind-таблицам,
сохранение лога в память, символизация по ELF на хосте.

**Критерий закрытия:** паника печатает цепочку вызовов с адресами.

---

### TD-027 — Только BSP, нет SMP

**Где:** всё ядро (глобальные `static mut`, один GDT/TSS/IDT).

**Почему так:** этап M1 — однопроцессорный.

**Последствия:** вторые ядра не поднимаются; нет ACPI/MADT, нет per-CPU
структур; код нельзя просто запустить на SMP.

**План:** M5+ — ACPI, AP bring-up, per-CPU GDT/TSS/стеки, спинлоки.

**Критерий закрытия:** QEMU с `-smp 2` поднимает оба ядра и выполняет задачи
на них.
